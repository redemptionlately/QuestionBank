## 2. 项目定位与价值

系统处理用户有权使用的试卷和答案资料，将其转成可人工审核的结构化题库，提供在线练习、
确定性判分、错题复习，以及后期可审计的主观题辅助反馈。

```text
受控文件输入
-> 可恢复异步导入
-> 可追溯题号切分与答案匹配
-> 人工审核和版本化发布
-> 在线作答与幂等提交
-> 规则判分和错题闭环
-> 可选 Agent 建议，不替代正式裁决
```

它的后端训练价值来自：REST 契约、鉴权、数据库建模、事务、索引、幂等、状态机、大文件、
对象存储、异步任务、线程池边界、失败恢复、缓存、限流、测试、可观测性和压测。Agent 只是
可替换外部依赖，不能成为系统正确性的来源。

### 与限量预约项目的关系

本项目可覆盖预约服务的大部分通用后端训练点：权限、幂等、唯一约束、事务、状态机、限流、
异步削峰、缓存、压测和部署。但它**不能天然等价**于热点库存扣减、超卖控制和秒杀流量模型。

- 若目标 JD 只要求通用 Java 后端能力，本项目完成可靠性阶段后可替代普通预约练习项目。
- 若目标 JD 高频要求库存扣减/秒杀，需要在本项目中增加“配额领取”独立实验，或单独做一个
  小型并发实验；不能拿文件去重冒充库存一致性。

## 3. 用户、信任边界与成功标准

### 3.1 用户

- 学生：浏览已发布题库、创建练习、保存草稿、提交、查看得分和错题。
- 管理员：上传授权资料、查看导入候选、修正题目/答案、审核并发布版本。

第一版不开放普通用户上传和公开分享，先把文件风险、权限和审核范围收小。

### 3.2 信任边界

- PDF 文本是不可信输入，可能巨大、损坏、加密、伪装类型或构造为解析消耗攻击。
- 解析器、对象存储、Redis 和模型 API 都可能超时或失败。
- 客户端提供的题号、分数、角色、文件名、幂等键都不能直接信任。
- Agent 输出是不确定建议，不能直接修改标准答案或最终成绩。
- 用户上传不代表平台拥有传播权，必须限制来源、访问和保留范围。

### 3.3 产品成功标准

核心版本完成时，一名管理员能导入一对受支持的文本型 PDF，审核候选并发布；一名学生能完成
一套题、得到确定性得分并形成错题记录。服务重启、重复请求或单个解析失败不能生成重复正式
数据或破坏已发布版本，关键操作有可追溯记录。

## 4. 范围分层

### 4.1 M0：最小业务闭环，不接 PDF

先证明普通 Java 后端能力：

1. 用户登录和 `STUDENT` / `ADMIN` 权限。
2. 管理员手工创建题库、试卷、单选/多选/判断题和标准答案。
3. 发布不可变的试卷版本。
4. 学生创建练习会话、保存答案并幂等提交。
5. 服务端确定性判分，错误题进入错题记录。
6. MySQL 迁移、集成测试、统一错误响应和 Docker 启动。

M0 不要求 Redis、MinIO、PDFBox、异步线程池或 Agent。先让核心业务和事务边界成立。

### 4.2 M1：受控 PDF 导入

1. 仅管理员上传文本型试卷 PDF 和答案 PDF。
2. 文件流式写入临时区/对象存储，限制字节数、页数、处理时间和并发数。
3. 持久化导入任务，后台提取文本并按明确题号生成候选。
4. 候选保留来源文件、页码、文本偏移、匹配规则和原因。
5. 管理员逐条编辑、接受或拒绝；只有一次事务性发布才进入正式题库版本。
6. 进程重启后，未完成任务可以被检测、恢复或明确失败。

### 4.3 M2：可靠性与并发证据

1. 上传、创建任务、提交练习和发布操作有明确幂等语义。
2. 数据库唯一约束作为重复创建的最终防线。
3. 受控线程池采用有界队列、拒绝策略和可观测队列深度。
4. 任务有租约/心跳、超时、有限重试和人工重放；不无限重试。
5. Redis 只在有明确问题时加入，例如高成本操作限流、短期草稿或热点查询缓存。
6. 固定条件压测记录 QPS、p50/p95/p99、错误率；异步任务额外记录排队与完成时间。
7. 完成一次单变量优化或“优化未生效”的诚实复盘。

### 4.4 M3：Agent 辅助批改

M3 分两次决策，不因已经学习 Harness 就默认接入：

1. **M3A 直接调用 Baseline**：主观题进入独立任务；模型按固定 JSON Schema 返回建议分、
   理由、评分点引用、不确定性和模型/Prompt 版本。
2. **M3B Harness 可选接入**：只有 Baseline 暴露出真实的多步取数、工具审计或上下文管理问题，
   才通过 `GradingAgentPort` 增加 Harness 适配器。
3. 人工可接受、修改或拒绝建议，所有模型、Prompt、工具调用、建议和人工操作分版本保留。
4. 模型超时、限流、无效 JSON、Harness 进程退出或不可用时，任务进入可解释状态，不影响基础
   练习、客观题判分和历史正式结果。
5. 使用同一冻结评测集比较 Direct 与 Harness；没有评测数据时不声称“准确批改”，没有对照
   证据时不声称 Harness 提升质量或效率。

### 4.5 M4：可选增强

- 扫描件 OCR 和数学公式识别。
- 用户通过官方 OAuth/API 或授权直链导入个人网盘文件。
- 浏览器扩展把网页题目保存为草稿候选，用户确认后入库。
- 编程题沙箱、独立 Worker/MQ、全文搜索等。

M4 每项都必须由真实用户需求、容量或故障证据触发，不按技术清单全部实现。

### 永久禁止或不默认做

- 绕过登录、验证码、付费墙、反爬、分享限制或访问控制抓取网盘资料。
- 未经授权抓取、公开或分发试卷和答案。
- 让 Agent 无人工规则或审核直接修改标准答案、正式分数或题库。
- 一开始使用微服务、Kubernetes、Kafka、向量数据库、多 Agent、自我蒸馏或模型微调。
- 浏览器扩展读取所有页面、账号 Cookie 或与保存题目无关的内容。

## 5. 架构：模块化单体优先

```text
Browser UI
  -> Spring Boot REST API
      -> identity/access
      -> bank/paper/version
      -> practice/grading/wrong-book
      -> import/review
      -> audit/observability
      -> MySQL                 source of truth
      -> local filesystem or MinIO   binary objects
      -> bounded worker executor     durable jobs in MySQL
      -> Redis only after M0/M1 need is proven
      -> PDFBox adapter
      -> GradingAgentPort
           |-> DirectModelAdapter      HTTP Baseline
           `-> HarnessProcessAdapter   JSON-RPC stdio, optional
                   -> restricted DeepSeek Harness runtime
```

### 5.1 模块责任

| 模块 | 责任 | 不允许做 |
|---|---|---|
| Identity/Access | 登录、角色、资源级授权 | 只在前端隐藏按钮代替鉴权 |
| Bank/Version | 题库、试卷、题目、答案、发布版本 | 原地修改已被作答引用的版本 |
| Practice/Grading | 会话、答案、提交、规则判分、错题 | 信任客户端分数或重复生成成绩 |
| Import | 文件元数据、任务、提取、切分、匹配 | 在 Web 请求线程解析大 PDF |
| Review/Publish | 候选审核、事务性发布、审计 | 解析完成后自动污染正式题库 |
| Agent/Grading Suggestion | 任务、运行、候选建议、人工复核 | 让模型直接写正式分数或题库 |
| Infrastructure adapters | 存储、PDF、Redis、模型/Harness 协议 | 让第三方类型侵入核心领域模型 |

### 5.2 为什么不用内存任务队列作为事实来源

受控线程池只负责执行，任务事实保存在 MySQL。仅用 `@Async` 或内存队列会在进程退出时丢失
任务，也难以安全重试。第一版可由单实例 worker 轮询/领取任务，但领取必须原子化，并记录：

```text
status / available_at / lease_owner / lease_until
attempt_count / max_attempts / last_error / started_at / finished_at
```

Worker 领取后获得有限租约；超时任务可被回收。处理结果写入要幂等，避免“任务已成功但状态
更新前进程崩溃”导致重复发布。若未来多实例竞争，再根据数据库能力选择条件更新、悲观锁或
`SKIP LOCKED`；选择必须用并发测试验证。

### 5.3 何时才引入 MQ

只有数据库任务表和单体 worker 已正确运行，并出现吞吐、隔离、重放或多消费者需求时，才评估
RabbitMQ/Kafka。引入后仍需处理至少一次投递、重复消费、幂等和死信，不把 MQ 当作自动可靠。

### 5.4 Agent 进程与协议边界

领域层只依赖 `GradingAgentPort`。`DirectModelAdapter` 先建立可测 Baseline；可选的
`HarnessProcessAdapter` 由 Java 使用 `ProcessBuilder` 管理长期子进程，通过 stdin/stdout 上
逐行 JSON-RPC 通信。stdout 只承载协议帧，stderr 有界保留用于诊断，凭据通过受控环境变量提供。

DeepSeek Harness 当前 SDK 协议处于预发布阶段，没有逐提示结果、取消和逐会话关闭。第一版因此
固定一个运行时同一时刻只处理一个在途业务任务；超时、非法帧或进程退出时回收并重建进程，
业务任务进入有限重试或人工处理。只有固定条件并发测试证明串行运行时是瓶颈，才引入有界进程
池；不能直接在一个事件流上并发后猜测响应归属。

Harness 第一版只暴露两个领域工具：按 `run_id` 读取已授权且版本化的批改上下文，以及提交候选
建议。不得提供 Bash、任意文件读写、任意 SQL、任意 URL 或正式成绩发布能力。

## 6. 核心数据模型与不变量

字段、DDL、外键、索引和迁移必须由用户自己设计。以下是模型责任，不是可复制 SQL。

| 聚合/实体 | 关键责任 | 关键约束 |
|---|---|---|
| `user_account` | 身份、密码摘要、状态 | 登录标识唯一；禁用状态不能登录 |
| `role` / membership | 系统角色、题库权限 | 后端资源级鉴权 |
| `question_bank` | 题库元数据和所有权 | 归档不删除历史版本 |
| `paper_version` | 一次不可变发布快照 | 发布号在题库内唯一 |
| `question_version` | 题干、题型、选项、分值、来源 | 发布后不原地修改 |
| `answer_key_version` | 标准答案、解析、规则版本 | 与题目版本绑定 |
| `practice_session` | 用户、试卷版本、状态和时间 | 只能提交一次有效最终版本 |
| `submission_item` | 某题草稿/最终答案 | `(session, question_version)` 唯一 |
| `grading_result` | 分数、规则版本和依据 | 绑定提交与答案版本 |
| `wrong_question` | 错题聚合状态 | `(user, question_identity)` 唯一，保留历史事件 |
| `stored_object` | 文件元数据、对象 key、哈希、所有者 | 哈希不能跨用户泄露文件存在性 |
| `import_job` | 持久任务、状态、租约、重试 | 用户作用域幂等键唯一 |
| `question_candidate` | 解析候选与来源定位 | 未审核不能进入正式版本 |
| `review_record` | 谁在何时做了什么决定 | 追加式审计，不静默覆盖 |
| `agent_run` | job/session、模型/Prompt/适配器版本、事件引用、成本和状态 | 与正式判分分离，可重放审计 |
| `grading_suggestion` | 结构化建议、评分点引用、Schema 版本 | 同一 run 最多一个生效候选，仍需人工复核 |

### 6.1 必须保持的不变量

- 已发布题目、答案和评分规则不可原地修改；新内容创建新版本。
- 历史作答永远能找到当时使用的题目、答案和规则版本。
- 同一个练习会话最多有一次生效的最终提交；网络重试返回同一业务结果。
- 候选数据只有通过授权管理员审核，才能原子发布为完整试卷版本。
- 删除文件不能留下悬空引用；删除策略和对象存储清理要可重试。
- 幂等键必须绑定用户、操作和请求摘要，不能让攻击者复用键获取他人响应。
- Agent 只能读取任务创建时冻结的版本；重复运行不能覆盖人工结论或产生两个生效建议。

### 6.2 事务边界

至少亲手设计和验证：

1. 发布试卷版本：题目、答案、版本状态要么一起成功，要么一起回滚。
2. 提交练习：冻结提交、生成评分和更新错题不能留下互相矛盾的半状态。
3. 创建导入：对象元数据与任务记录要有失败补偿；数据库事务不能包住长时间对象上传。
4. Agent 调用：外部网络请求不能放在长数据库事务中；用任务状态衔接。

若事务提交后需要发送任务或事件，先使用可审计的数据库状态/Outbox 思路，再讨论分布式方案。

## 7. API 与错误契约

具体 URI 由用户设计，但第一版至少需要以下资源行为：

| 行为 | 关键输入 | 成功语义 | 必须覆盖的失败 |
|---|---|---|---|
| 登录 | 凭证 | 建立受控会话/Token | 错误凭证、禁用、限流 |
| 创建/编辑草稿题库 | 题目与答案 | 草稿可修改 | 校验失败、越权、版本冲突 |
| 发布版本 | 草稿版本、幂等键 | 生成不可变版本 | 未审核、重复发布、并发冲突 |
| 创建练习 | 试卷版本 | 返回会话 | 未发布、无权限 |
| 保存答案 | 会话、题目、答案、版本 | 可重复覆盖草稿 | 会话结束、题目不属于试卷 |
| 提交练习 | 会话、幂等键 | 只生成一次有效结果 | 重复、并发提交、过期 |
| 上传文件 | 文件流、用途 | 返回对象/上传状态 | 类型、大小、页数、配额、恶意文件 |
| 创建导入任务 | 两个文件引用、幂等键 | 返回持久任务 | 文件不属于用户、重复、队列容量 |
| 查询任务 | task id | 返回状态和可公开错误 | 越权、未知任务 |
| 审核候选 | candidate/version | 记录决定 | 非管理员、旧版本、非法状态 |
| 创建辅助批改 | submission/version、幂等键 | 返回持久任务 | 非主观题、越权、重复、过载 |
| 查询批改建议 | grading task id | 返回运行/复核状态 | 越权、未完成、依赖失败 |
| 复核批改建议 | suggestion/version、决定 | 追加人工结论 | 旧版本、重复决定、非法分数 |

统一错误响应至少包含稳定业务码、用户可读消息、请求追踪 ID；内部堆栈、SQL 和对象 key 不返回
客户端。HTTP 状态要有语义，例如参数错误 400、未认证 401、越权 403、不存在 404、版本/状态
冲突 409、过载/限流 429、服务依赖不可用 503。

## 8. 状态机

### 8.1 导入任务

```text
CREATED -> QUEUED -> PROCESSING -> REVIEW_REQUIRED -> PUBLISHED
                         |                 |
                         v                 v
                       FAILED           REJECTED

FAILED -> QUEUED        仅人工或策略允许、未超过次数时
PROCESSING -> QUEUED     租约过期且任务可安全重放时
任意未结束状态 -> CANCELLED  仅尚未进入不可逆发布时
```

每个迁移都要规定触发者、前置状态、幂等行为、错误保存和审计。`PUBLISHED` 是业务发布完成，
不能只表示 PDF 文本提取完成。

### 8.2 练习会话

```text
IN_PROGRESS -> SUBMITTED
IN_PROGRESS -> EXPIRED
IN_PROGRESS -> ABANDONED
```

`SUBMITTED` 后答案不可原地修改；重做创建新会话。客户端自动保存不改变最终提交状态。

### 8.3 Agent 批改任务

```text
CREATED -> QUEUED -> RUNNING -> VALIDATING -> REVIEW_REQUIRED
                         |          |               |
                         v          v               v
                    RETRY_WAIT    FAILED      ACCEPTED / OVERRIDDEN / REJECTED

RETRY_WAIT -> QUEUED     仅错误可重试、租约有效且未超过次数时
任意未结束状态 -> CANCELLED  仅尚未产生人工生效结论时
```

模型建议和人工最终结果分表、分版本保存，不把“置信度”伪装成校准概率。Harness session 的
`running/idle` 是外部运行状态，不直接替代 Java 任务状态；Java 只有在 Schema、版本、权限和
评分点引用校验后，才能从 `VALIDATING` 进入 `REVIEW_REQUIRED`。

## 9. PDF 提取与题号匹配

### 9.1 支持矩阵

第一版只接受可提取文本且未加密的 PDF。导入开始前记录：字节数、页数、是否加密、提取字符数
和失败原因。若页面几乎没有文本，明确标记 `OCR_REQUIRED`，不返回“解析成功但没有题”。

### 9.2 可追溯解析

每个候选保存：

```text
normalized question number
source object/version
page number and character offsets
raw question/answer fragments
parser and rule version
match method, warnings and reason
```

第一版先支持明确编号，如 `1.`、`1、`、`（1）`，但要区分主问题号和子问题号。答案缺失、
重复题号、跨页、顺序错位和题数不一致都进入审核警告。所谓置信度必须有定义；若没有校准，
使用 `EXACT / AMBIGUOUS / UNMATCHED` 等可解释等级比伪造小数更可靠。

### 9.3 发布规则

高置信候选也不能自动发布。管理员看到原始片段和来源页，修正后形成新的结构化草稿；发布时
重新校验题号唯一、题型、选项、分值与答案完整性。

## 10. 判分与 Agent 评估

| 题型 | 核心版本 | 后续 |
|---|---|---|
| 单选/判断 | 归一化后精确匹配 | 无需 Agent |
| 多选 | 集合匹配，评分规则版本化 | 可配置部分分 |
| 填空 | 暂不自动判或仅支持明确定义规则 | 数值/表达式工具校验 |
| 简答 | 不自动形成正式分数 | Agent 建议 + 人工审核 |
| 编程 | 不支持 | 隔离沙箱运行测试，不由模型直接裁决 |

### 10.1 Baseline-first Gate

先使用 `DirectModelAdapter` 完成一次结构化调用，不加载 Agent tools。它必须具备固定 Prompt 与
Schema 版本、超时、最大输出、有限重试、Mock 契约测试和原始评测记录。若单次调用已满足当前
质量、审计与恢复要求，Harness 不进入业务路径。

### 10.2 Harness 引入 Gate

只有出现以下至少一个可复现问题，才实现 `HarnessProcessAdapter`：

- 批改上下文不能安全放入一次请求，需要按授权通过多个只读工具分步获取。
- 需要保存工具参数、结果与多 step 决策过程，单次请求日志无法满足审计。
- 长上下文需要可验证的 session/compaction 行为，而不是简单截断。

“更像 Agent”、框架热门或插件多不是引入理由。接入后必须用相同模型、输入、评分规则、超时
和最大输出，与 Direct Baseline 做 A/B；若收益不能覆盖进程、协议、延迟和运维复杂度，应回退。

### 10.3 冻结评测集

必须先准备一组经人工确认、不得出现在 Prompt 示例中的评测样本，并冻结：题目、评分点、参考
答案、学生答案和人工结论。至少评估：

- 结构化输出有效率、超时率和失败率。
- 建议分与人工分的 MAE/一致率，按题型和分值分层。
- 评分点引用是否来自提供材料，是否出现无法支持的依据。
- 同一输入重复运行的波动。
- 成本与延迟分布。
- 人工接受、修改和拒绝比例。

数据量不足时只报告样本结果和局限，不声称达到通用准确率。模型升级或 Prompt 变化必须记录
版本并重新评估。Agent 内容视为不可信数据：严格 schema 校验、长度限制、超时、重试上限、
输出转义和审计；来自 PDF 的文字不能变成系统指令。

## 11. 安全、隐私与合规

- 只处理用户有权使用的资料；提供删除与保留策略，不默认公开题库或文件。
- 上传使用流式读取和服务端生成对象 key；限制请求体、文件大小、页数、解析时间和并发数。
- 不能只信扩展名或客户端 MIME；检查文件签名和解析结果，隔离临时文件。
- PDF 解析放在低权限、资源受限的 Worker；生产思路需考虑恶意 PDF 扫描和依赖漏洞升级。
- SHA-256 用于完整性/去重提示，不作为访问权限；不能让哈希命中泄露别人是否上传过文件。
- 对象下载必须鉴权并使用短期授权；日志不记录密码、Token、完整答案或敏感原文。
- 密码使用现代自适应哈希；密钥、数据库密码和模型 Token 不进入 Git。
- 登录、上传、导入、提交和 Agent 调用分别设计限流/配额，管理员操作也要审计。
- Harness 工具使用显式 allowlist；第一版不加载 Bash、任意文件写入、任意网络和自修改能力。
- Java 启动子进程时使用环境变量白名单、固定工作目录和资源上限；stdout 协议与 stderr 日志分离。
- Prompt、PDF、题干和学生答案中的指令性文字只作为数据，不得改变系统规则或工具权限。
- 网盘只能通过官方 API/OAuth 或用户提供的合法授权直链；权限最小化，可撤销，不保存用户密码。
- 浏览器扩展仅在用户点击时读取当前题目所需内容，使用最小 host permissions，保存前预览。
- 依赖版本固定并做升级记录；备份和恢复要在后期真实演练，不能只写“支持备份”。

## 12. 测试与故障验收

### 12.1 测试层级

| 层级 | 覆盖重点 |
|---|---|
| 单元测试 | 题号解析、状态迁移、评分规则、值对象和边界 |
| Repository/数据库测试 | 唯一约束、索引查询、乐观/悲观并发和迁移 |
| API 集成测试 | 鉴权、校验、错误契约、幂等和事务回滚 |
| 存储/解析集成测试 | MinIO/文件系统、PDFBox、损坏/加密/空文本 PDF |
| 端到端测试 | 管理员发布到学生提交的最小业务闭环 |
| 并发/恢复测试 | 重复提交、worker 崩溃、租约过期、重试和服务重启 |
| Agent 适配器契约 | Direct Mock、假 JSON-RPC 进程、帧路由、退出和资源回收 |
| Agent 评测 | 冻结样本、Direct/Harness 同条件对照、人工复核和版本变化 |

优先使用固定、可合法提交的小型 PDF fixture。测试文件必须包含正常、重复题号、跨页、答案缺失、
加密/损坏和文本为空等情况；大文件性能样本若不能提交，提供生成方法和哈希。

### 12.2 必须主动注入的故障

- 对象保存成功但数据库创建任务失败。
- Worker 处理完成但更新状态前退出。
- 两个请求使用相同/不同幂等键并发提交。
- 发布事务中途抛错。
- Redis 不可用、模型 API 超时、PDF 解析超时。
- 服务重启后存在 `PROCESSING` 且租约过期的任务。
- Harness 握手失败、运行中退出、永远不进入 idle、输出非法/重复/错 id 协议帧。
- Agent 工具请求越权 run、过期版本或未允许能力，模型返回超长或越界建议。

每个故障要记录预期状态、实际数据库状态、是否可重试和是否产生重复副作用。

## 13. Benchmark 与可观测性

### 13.1 指标分层

同步 API：请求量、成功/错误数、p50/p95/p99、状态码、数据库耗时。

异步任务：队列深度、排队时间、处理时间、端到端完成时间、重试数、最终失败数、租约回收数。

业务质量：解析成功/失败、未匹配题数、审核修改率、发布失败率。Agent 阶段再加入评测指标，
不能用系统 QPS 替代批改质量。

Agent 运行：任务排队/运行/端到端时间、Schema 有效率、超时/重试/最终失败、子进程重启、
模型调用与 token、人工接受/覆盖/拒绝。人工接受率也不能自动等于准确率。

### 13.2 压测规则

- 固定 commit、机器、JVM、数据库/Redis/MinIO 版本、数据规模、请求体、并发、预热和持续时间。
- 区分接口接受任务的延迟与任务真正完成的时间。
- 记录客户端错误、服务端错误和超时，不能只计算成功请求 QPS。
- 一次只改变一个主要变量，例如 worker 数、队列容量或数据库连接池大小。
- 保存原始输出和配置，报告“测到、能证明、不能证明、下一步”。
- 压测数据要定期清理或使用隔离环境，防止历史数据影响索引和容量结论。

### 13.3 可观测性最低要求

- 结构化日志包含 request id、job id 和公开业务码，不包含敏感正文。
- 健康检查区分进程存活与依赖就绪。
- 至少能查询任务状态分布、队列深度、失败原因和接口延迟。
- 告警和 Dashboard 不是第一阶段要求；先证明指标可信。

## 14. 学习与实现阶段

每个阶段采用纵向切片：需求和失败场景 -> 数据模型/API -> 用户实现 -> 测试 -> 运行证据 ->
Review -> 用户复述。代码通过但用户讲不清，只算工程进展。

| 阶段 | 用户亲手交付 | 主要学习点 | 出口证据 |
|---|---|---|---|
| 0. 启动决策 | 触发证据、范围、时间预算、停止条件 | 产品范围、求职取舍 | 一页决策记录通过 Review |
| 1. 工程骨架 | Maven、Spring Boot、迁移、错误契约、Docker、健康检查 | Java 工程、配置、Git | 新环境启动和测试日志 |

| 3. 版本化题库 | 试卷草稿、题目/答案、审核与发布 | 事务、索引、版本不变量 | 回滚测试、`EXPLAIN`、发布测试 |
| 4. 在线练习 | 会话、草稿、幂等提交、规则判分、错题 | 状态机、幂等、并发 | 重复/并发提交测试和 E2E |
| 5. 文件与导入 | 受控上传、对象存储、持久任务、PDF 提取 | 流式 I/O、线程池、租约、恢复 | 重启/失败恢复和安全测试 |

| 8A. Direct Baseline | 结构化模型适配器、Mock、冻结样本 | 外部 API、Schema、成本与审计 | 首轮评测和失败分类 |

## 16. 代码所有权与 AI 协作

每次只给一个任务卡：目标、输入输出、数据约束、失败场景、验收命令和参考资料。

1. Allen 先复述需求、数据流和不变量。
2. Allen 写接口、核心代码、迁移和测试；不会时先写伪代码或最小片段。
3. AI 按提示阶梯协助：澄清 -> 小例子 -> 伪代码 -> 局部代码；默认不直接交付完整答案。
4. Allen 亲自运行格式化、测试、服务、Docker、压测和 Git 命令并解释输出。
5. AI Review 正确性、安全、事务、并发、测试和可维护性；Allen 修改后再进入下一切片。

AI 可以提供接口草图、伪代码、测试口径、故障清单、官方资料、Review 和报告模板，但所有
进入仓库的实现仍由 Allen 亲手编写。每个简历模块还要通过：复述、预测、亲手修改、正确性、
解释、变式和复现。

## 17. 可投递与停止标准

### 可写入 Java 后端简历的最低标准

- 阶段 1～4 完成，且用户能逐段解释核心数据流、事务和测试。
- 新环境能启动 MySQL + 服务并完成一条题库发布/练习 E2E。
- 至少有一个自己设计的索引及 `EXPLAIN`、一个事务回滚测试、一个幂等并发测试。
- README、迁移、测试和 Git 历史真实；简历只写自己负责范围。

### 可作为差异化项目的标准

- 阶段 5～7 完成：受控 PDF、持久异步任务、恢复、审核、限流/缓存和压测有证据。
- 能讲清一次崩溃恢复、重复消费/提交防护和一次性能未达预期的案例。
- Agent 未完成不影响项目成立；完成 Agent 时必须附评测集和人工审核边界。
- 若保留 Harness，必须能解释相对 Direct Baseline 的收益、协议限制、进程恢复和回退路径。

### 应暂停或停止的信号

- 连续两周只有框架/实体堆积，没有可运行纵向切片。
- 项目显著挤占已确定的 C++ 主线，却没有新的 JD 或投递证据支持。
- 技术组件数量持续增加，但事务、幂等、测试和用户理解没有进步。
- Harness 学习停留在插件目录浏览，未形成 Java 协议、故障或评测证据。
- 四周检查点无法说明新增的 `learned` 能力和求职价值。

停止不等于失败；保留证据，回到主投路线。
