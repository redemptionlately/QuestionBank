### Q2. 设计十万学生提交，算 QPS/连接数/队列。
**先做假设（必须显式写出）**：10 万学生集中在 2 小时完成提交，峰值是均值的 3 倍，单提交平均 50ms、每请求平均 6 条 SQL、单实例。
- 均值 QPS = 100000 / 7200s ≈ 14 QPS；峰值 ≈ 42 QPS；
- 由 Little 定律，峰值在途请求 L = λ×W = 42×0.05 ≈ 2.1；
- 每请求 6 条 SQL、每条 5ms，则每请求占用连接约 30ms，需要的 DB 并发 ≈ 42×0.03 ≈ 1.3，留余量配 10~20 连接即可（连接池不是越大越好）；
- 队列：异步导入/削峰队列按“峰值生产速率 × 可接受积压时长”估算容量。
所有数字都标注假设，改假设重算。

### Q3. 写出 SLO/超时/重试/限流/缓存/队列/降级/熔断/隔离舱的作用边界。
| 手段 | 控制对象 | 边界（不能解决什么） |
|---|---|---|
| SLI/SLO/SLA | SLI 测量值、SLO 内部目标、SLA 对外承诺 | 不直接提升性能 |
| 超时 Timeout | 单次等待上限 | 不保证成功，只快速释放资源 |
| 重试 Retry | 瞬态错误 | 会放大流量，非幂等/确定性错误不能重试 |
| 限流 RateLimit | 进入速率 | 不增加系统容量 |
| 缓存 Cache | 降低读成本 | 有一致性窗口，不是事实来源 |
| 队列 Queue | 削峰填谷、异步解耦 | 只是把压力后移，需消费能力兜底 |
| 降级 Fallback | 故障时提供有限能力 | 是有损服务 |
| 熔断 CB | 故障扩散范围 | 不修复下游，只给其恢复时间 |
| 隔离舱 Bulkhead | 资源（线程/连接）隔离 | 单舱资源更少，需合理分配 |

### Q4. 用 Little 定律和连接池上限估算提交接口容量。
设连接池大小 P、每请求平均占用连接时间 D（秒），则数据库侧吞吐上限 λ_max ≈ P / D。例：P=20、D=0.03s → λ_max ≈ 666 QPS 的理论上限（实际还受锁、CPU、下游约束）。连接池容量**不等于** Tomcat 线程数：线程可在不访问 DB 时处理别的，但一个请求访问 DB 时必须持有连接；决定因素是 DB 最大连接数、每请求 SQL 数、事务持锁时间与尾部延迟。

### Q5. 比较模块化单体与微服务的事务/网络/部署成本。
| 维度 | 模块化单体（本项目） | 微服务 |
|---|---|---|
| 调用 | 进程内方法调用，快、简单 | 网络 RPC，有序列化/超时/重试成本 |
| 事务 | 本地 ACID 事务即可保证一致 | 需 Saga/最终一致/分布式事务，复杂 |
| 部署 | 整体部署，调试简单 | 独立部署、独立扩缩，需 CI/CD 与治理 |
| 数据 | 同库，聚合边界清晰 | 每服务一库，跨服务一致性难 |
| 适用 | 团队/流量规模小，领域可分包隔离 | 有明确流量、团队、故障隔离或数据所有权证据才拆 |
没有证据时优先模块化单体（本项目 auth/bank/practice/common 分包即此思路）。

### Q6. 用 ss/lsof/curl -v/top/vmstat 设计一次 TCP/HTTP 排障，并解释五段耗时。
```bash
ss -lntp                 # 看端口是否监听、连接状态、进程
lsof -i :8080            # 看谁占用端口
curl -v https://host/api # 看 DNS 解析、TCP 建连、TLS 握手、请求/响应
top / vmstat 1           # CPU、运行队列、上下文切换、内存/swap
journalctl -u app -f     # 服务日志
```
**五段延迟（分别测量，不能把总耗时都算给应用代码）**：
1. DNS 解析（域名→IP）；2. TCP 建连（三次握手 RTT）；3. TLS 握手（证书、密钥交换，额外 RTT）；4. HTTP 请求发送 + 服务端处理（应用/DB）；5. 数据库等待（连接获取、锁、SQL）。curl `-w` 可输出 namelookup/connect/appconnect/starttransfer 各段时间。

### Q7. keep-alive、连接复用、TIME_WAIT 的影响。
- **三次握手**：客户端 SYN → 服务端 SYN-ACK → 客户端 ACK；
- **四次挥手**：主动方 FIN → 被动方 ACK → 被动方 FIN → 主动方 ACK；**主动关闭方**进入 `TIME_WAIT`，持续 2MSL，期间该四元组（src/dst ip+port）不能复用；
- 短连接高并发时主动关闭方累积大量 TIME_WAIT，占用本地端口；**keep-alive / 连接池复用**连接，减少握手与 TIME_WAIT、摊薄 TLS 成本；服务端也要设置空闲连接超时，避免僵死连接占资源。

### Q8. 反向代理 X-Forwarded-* 的信任前提与伪造风险。
`X-Forwarded-For/X-Forwarded-Proto` 是**可被客户端任意伪造**的头。只有当连接确实来自可信代理（Nginx/网关），且应用只信任代理覆盖的值、移除客户端自带的同名头时，才能用它识别真实 IP/协议。配置：代理 `proxy_set_header X-Forwarded-For $remote_addr;`，应用配置可信代理网段（如 Spring `server.forward-headers-strategy` 并限制受信代理）。否则攻击者可伪造 IP 绕过基于 IP 的限流/审计。反向代理负责连接终止、TLS 卸载、路由与超时。

### E2. 画 TCP 三次握手/四次挥手/TIME_WAIT；用命令解释异常。
- 端口没监听：`ss -lntp` 无记录 → curl Connection refused；
- TLS 异常：`curl -v` 在 SSL handshake 阶段报错（证书过期/链不全/SNI）；
- 资源异常：`vmstat` 的 r 列长期大于核数（CPU 排队）、si/so 非零（swap）、`top` 看进程 CPU/内存；据此区分是监听问题、TLS 问题还是资源瓶颈。
